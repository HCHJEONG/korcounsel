## 최초 후속 계획 (1~2는 이번 제한 교정 완료, 3~5는 후속)

### 1. 현재 DB·artifact 기준선 재집계

위 집계 기준으로 실제 현재 상태를 확인한다. 판례 수, revision 수, job 수를
별도 열로 둔다. 기존 문서의 시점별 숫자와 다르면 삭제하거나 덮지 말고 새로운
시점·SQL·원인을 기록한다.

### 2. lawgo 동일성 충돌과 제공 조문 구조 실패 정리

433건 품질 보고서에서 lawgo 동일성 충돌, 조문 미연결, 구조 변경 실패,
법령 버전 미확인을 유형별로 다시 고정한다. 기존 문서에는 초기 23건의 충돌
3건과 410건 품질 점검의 별도 충돌/구조 실패 수가 시점별로 존재하므로 합산을
추정하지 말고 현재 보고서와 DB에서 재집계한다.

- 후보의 법원·사건번호·재판 종류·선고일·제공자 ID를 보존 근거와 대조한다.
- EXACT로 확인된 제공 연결만 조문 보강에 사용한다.
- 앱이 본문 인용을 추론해 법령 API를 호출하지 않는다.
- 충돌·미제공·구조 변경은 판례 수집 실패로 바꾸지 않는다.
- 결정론적으로 고칠 수 있는 새 응답 형식이면 parser fixture와 새 immutable
  reader/field revision을 만든다. 원본과 과거 revision은 유지한다.

### 3. 폐기 판례 역참조 감사 설계와 제한 실행

repealed_cases는 현재 REVIEW다. 먼저 전체 corpus에서 어떤 공식·보존 근거로
폐기/변경 관계를 확정할 수 있는지 계약을 작성한다. 단순 문자열 인용이나
부재를 근거로 미폐기 값을 만들지 않는다. 작은 고정 표본으로 projection과
재실행 idempotency를 검증한 뒤 전체 실행 여부를 별도로 판단한다.

### 4. 기존 사건기호의 역사적 적용 가능성 조사

신규 433건의 case-fields-6 구현은 완료됐다. 남은 것은 legacy 89,130건의
역사적 기호다. 사건기호·선고연도·법원·기존 case_sort·lawgo 사건종류를
읽기 전용으로 교차 집계해 충돌과 미분류를 먼저 분리한다. 2022-07-29 이전
자료는 당시 시행 예규를 확보하기 전까지 REVIEW로 둔다. 현재 공식표만으로
과거 유효성을 단정하거나 89,130건을 즉시 재발행하지 않는다.

### 5. 다음 연속 수집 구간 결정

수정 가능한 오류 검증과 미해결 항목의 근거·보류 기록을 마치고, 별도 명시

후보 구간으로 inventory한다. 먼저 월별 목록 수, legacy/현재 source와의 중복,
