# scourt 기본 본문·lawgo 보강·증분 축적 전략

2026-09-10 사용자 결정: 기존 약 9만 건을 scourt 기반 본문에 lawgo 정보를 보강한 자산으로 계승한다. 기본 전략을 KorCounsel에서 재사용하되, 원자료와 보강 결과·완료 상태·변경 이력을 분리한다. 이 문서는 과거 코드/저장본 관찰과 새 구현 계획을 구분한다.

## 이미지 주소 보완의 뜻

HTML의 `src="/wsjodocs/.../image.png"`는 해당 웹사이트 루트 기준 상대주소다. scourt 화면에서는 scourt 도메인을 기준으로 해석되지만, 파일로 열거나 다른 앱에서 표시하면 같은 주소로 해석되지 않는다. `src="https://glaw.scourt.go.kr/wsjodocs/.../image.png"`로 만들면 어느 사이트의 이미지를 가리키는지 명시할 수 있다.

`_06_crawl_lawgo_jomun_image.py:294`는 정확히 `casestr.replace('src="/', 'src="https://glaw.scourt.go.kr/')`를 실행한다. 이미지 자체를 lawgo에서 대체하거나 다운로드하는 코드가 아니라 scourt 주소를 보완하는 코드다. 모든 상대주소 종류를 처리하지 않고, 작은따옴표·../·srcset 등은 이 치환으로 해결되지 않는다. 절대주소만으로 현재 URL 접근성·영구 보존·원문 완전성을 보증하지 않는다.

저장본에서도 확인했다. `glaw_updated_panre_txt/3328392.txt`에는 `/wsjodocs/images/contents/alert_img_01.png`가 4개 있고 jtable은 없다. 대응 보강본 `lawgo_jomunupdated_panre_txt/88590-3328392-240889.txt`에는 동일 경로의 scourt 절대주소 4개와 HTML 조문 표를 담은 jtable 11개가 있다. 이 이미지들은 UI 안내 이미지 표본이므로 법적 그림의 존재·완전성 근거로 사용하지 않는다. [표본 경로·해시·속성 집계](step0/legacy-enrichment-samples.json)를 보존했다.

## 레거시의 내용 보강 흐름

1. `_01`에서 scourt 목록 JSON과 lawgo 공식 목록 XML을 취득해 각각 contId·판례일련번호를 보존한다.
2. `_02:86–124`에서 contId로 scourt 상세 화면을 열고 제목·본문·부가정보 HTML을 저장한다.
3. `_03:693–719`에서 HTML과 추출 텍스트를 나누고 판시사항·요지·이유 등을 추출한다. `_04`에서 기존 corpus와 신규 행을 합친다.
4. `_05:76`에서 법원·사건번호·날짜 대조로 대응 lawgo 판례일련번호를 lmeta_serialno에 그대로 연결한다.
5. `_06:92–132`에서 scourt의 linkContJomun 링크와 lawgo 상세 HTML의 조문 링크를 표시 텍스트와 순서로 대응시킨다. lawgo iframe 및 조문 popup을 사용한다.
6. `_06:223–227`에서 조문 표 HTML을 scourt 링크의 jtable 속성에 넣는다. 실패하면 사유 문자열을 남긴다. 기존 scourt 본문을 법제처 판례 전문으로 전부 교체하는 흐름은 아니다.
7. `_06:387`에서 `{행번호}-{contId}-{serialno}.txt`로 저장하고 `_07:28–37`에서 행번호로 corpus의 HTML 필드를 갱신한다. 기존 추출 텍스트를 이 단계에서 모두 다시 만드는 것은 아니다.

따라서 사용자의 해석처럼 **scourt 기본 본문 + scourt 이미지 참조 보완 + lawgo 조문 내용 보강**이 핵심 전략이다. scourt에 조문 링크/인용 자체가 없었다는 뜻은 아니다. 실제로 그 링크를 대상으로 lawgo의 상세 조문 표를 추가한다. scourt에서 조문 내용을 취득할 수 없었던 모든 원인이나 source 전체의 우열은 코드만으로 확정하지 않는다.

표본 세 보강 파일의 jtable 12개/11개/12개 모두 표 HTML을 담고 있었다. 전체 corpus의 성공률·완전성이나 당시/현재 적용 법령 버전 일치율을 측정한 결과는 아니다. 내용 보강이 이뤄진 자료라는 점과 모든 보강이 검증 완료라는 주장은 구분한다.

## 이미 구현된 증분 전략과 한계

| 기능 | 실제 코드 | 계승할 의미 |
| --- | --- | --- |
| 신규 scourt ID 탐지 | `_02:28–34` 기존 contId 집합과 최신 목록 차집합 | 기존 원문을 매번 다시 받지 않고 신규만 취득 |
| 기존 corpus 누적 | `_04:515` 기존+신규 concat | 초기 corpus 위에 축적 |
| 기존 lawgo 연결 재사용 | `_05:27` empty/0인 연결만 매칭 | 확보된 공식 ID를 유지 |
| 보강 미완료 선택 | `_06:434–437` success 표시 없는 HTML만 대상 | 완료 보강은 반복하지 않음 |
| 중단 후 재개 | `_06:455–465` 이미 저장한 보강 파일의 contId를 제외 | 완료 산출물 활용 |
| 추적 파일명 | `_06:387` row-contId-serialno | 행·두 source ID 연결 흔적 보존 |

신규 판례 증분의 직접 기준은 scourt contId였다. 두 ID 각각의 신규·변경·삭제를 모두 추적하는 대칭적 증분 엔진은 아니었다. serialno는 대응 판례 및 조문 보강 접근키다. `_06`에는 lawgo metadata를 다시 매칭하는 분기도 있다.

그대로 복사하지 않을 구현: HTML success 문자열을 모든 조문 성공으로 해석, 같은 ID의 변경 본문을 놓치는 방식, 행번호만으로 최종 반영, 경로 문자열 split에 의존하는 재개, 기존 HTML 덮어쓰기, 의미 확인 없는 첫 후보 매칭. 12개 병렬 browser 기본값도 단일 small EC2 운영 설정으로 계승하지 않는다.

## KorCounsel에서 채택하는 전략

```text
기존 89,130행 + 두 공식 ID + 보강 HTML + 원래 row locator
    → 보존 import / 업무키·결정 문서·source alias 연결
    → scourt inventory와 기존 ID 비교
    → 신규 본문 + 이전 상세 실패만 취득
    → lawgo 연결 재사용·미연결 후보 대조
    → 이미지 reference 주소 해석 / 조문 미보강분 보강
    → 기존 판례 원문과 별도 보강 artifact·manifest 저장
    → 다음 실행에서 신규·실패·변경분만 이어서 처리
```

- 기본 본문은 scourt를 우선하며 기존 corpus를 baseline으로 사용한다. lawgo는 metadata 연결·조문 보강 source이며 별도 전문 representation도 보존할 수 있다. lawgo-only·LawnB 자료를 배제하지 않는다.
- 기존 contId·serialno를 그대로 유지하고 출처 namespace를 구분한다. 법원명+사건번호 업무키, 개별 결정 문서, canonical 대표값과 legacy locator 계약을 유지한다.
- 기존 보강 결과도 import한다. 이미 들어 있는 jtable을 버리고 처음부터 다시 수집하지 않는다. 과거 취득시각/법령 버전이 없으면 미확인으로 표시한다.
- 원본 artifact와 lawgo 조문 artifact, 둘의 결합 결과를 각각 보존한다. 각 조문 보강은 부모 판례 artifact/hash·위치/링크·serialno·조문 식별/버전·취득시각·규칙 버전·상태에 연결한다. 취득한 조문을 그 판결 당시 적용 법령이라고 자동 단정하지 않는다.
- 이미지 original_src와 해석된 URL을 별도 보존한다. HTML base URL을 기준으로 해석하며 새 앱 도메인을 기준으로 삼지 않는다. 실제 binary 취득은 별도 ledger/단계이며 private viewer가 임의 외부 이미지를 자동 로드하지 않는다.
- 본문 취득, source 연결, 조문 항목별 보강, 이미지 reference/asset 상태를 따로 관리한다. 일부 조문/asset 실패로 확보된 판례를 버리지 않는다.
- scourt 신규·미완료 취득과 기존 본문 refresh를 분리한다. 같은 ID라도 실제 원문 hash가 달라지면 새 버전을 보존한다. 부분 inventory에서 삭제를 추정하지 않는다.
- 보강 재실행 키는 부모 source/artifact version + 보강 대상 + 선택된 조문 version 또는 미확인 관찰 식별자 + 규칙 version이다. 기존 판례 내용·연결·조문 버전이 바뀌면 관련 보강만 다시 평가한다. 지금 최신 조문으로 과거 보강을 덮어쓰지 않는다.
- 법제처 목록 변화는 미연결 판례의 재대조·보강 재시도 계기로 활용한다. 새 lawgo ID가 곧바로 새 법적 판례를 뜻하지 않는다. 업무키/문서/기존 alias와 대조한다.

## 구현 순서와 검증

bootstrap 계약 확정 → 보존 import/DB ledger → 두 source adapter 검증 → identity 연결 → 초기 조문 보강 단계 순으로 구현한다. 법제처 API client를 먼저 개발할 수 있다는 기존 순서는 기술 검증 순서이며 corpus 기본 출처를 법제처로 바꾸는 결정이 아니다. live scourt 접근 전략은 현재 동작·이용 조건 확인 후 고정한다.

완료 기준은 같은 입력 재실행 시 본문·보강 중복 없음, 실패 항목만 재시도, 이미지 상대주소/절대주소·../·srcset 별도 테스트, 조문 일부 실패·버전 미확인 보존, 본문 hash 변경 시 보강 revision 분리, 종료/checkpoint 후 재개, 기존 raw/보강 이력 유지다. 이번 작업은 코드/저장본 확인과 설계 기록이며 KorCounsel 수집·보강·증분 실행을 구현하거나 live 검증한 것은 아니다.


## 확정한 보강 범위와 선등록 — 사용자 결정 2026-09-10

- 인용이 확실해 보여도 앱이 법령명·조항·적용 버전을 스스로 해석해 법령 API에서 직접 보강하는 전략은 채택하지 않는다. 기존 자료와 신규 자료의 일관성을 유지한다.
- 법원과 법제처가 해당 판례에 제공하는 본문·인용·연결·조문 정보를 출처와 함께 보존·결합하는 범위에 한정한다. 제공자가 붙이지 않은 판례→조문 연결이나 법적 의미를 생성하지 않는다. 수집 형식·프로토콜의 변경과 내용 보강 범위의 확대는 별개다.
- scourt 본문은 기본 검증 후 먼저 등록해 조회·검색·검수에 사용한다. lawgo 미등록/미연결/미보강 때문에 판례 등록을 막지 않는다. UI에 본문 확보와 보강 대기/부분 완료/완료/실패를 별도로 표시한다.
- 법제처에 자료가 추가되면 대기 항목을 다시 대조하고 제공된 조문 정보만 별도 보강 revision으로 추가한다. 본문은 바뀌지 않았다면 다시 수집하지 않는다. 재시도는 목록 변화와 대기 기간에 따라 제한하며 구체적 주기는 운영 측정 후 정한다.
- 법제처에 끝내 대응 자료가 생기지 않아도 정상 미보강 판례로 보존한다. source 대기와 기술적 수집 실패를 구분한다. gold는 해당 쟁점에 실제 필요한 근거로 별도 평가한다.
- 법제처가 항상 scourt보다 늦거나 적다는 보장은 확인되지 않았다. 기관 간 전달 절차·실제 등록 시차는 추정과 관찰을 구분한다. 수집기 최초 관찰 시각도 source의 실제 게시 시각과 다르다.

## 현행 사이트 호환성은 별도 선행 검증

과거 성공한 전략과 과거 구현의 현재 작동 여부를 분리한다. 2024년 저장본과 코드가 존재해도 현재 scourt/lawgo HTML·내부 endpoint·세션·팝업·iframe이 같다고 가정하지 않는다. 현재 호환성은 미검증이다.

Step 3A에서 양쪽 경로를 검증한 뒤 대량 신규 수집·Step 5B 보강을 실행한다.

1. scourt 목록 endpoint·pagination/응답 schema·contId, 상세 화면의 제목/본문/부가정보·동적 로딩·세션·image base/src/첨부 경로를 확인한다. 옛 .page, bmunStart, areaNetwork는 조사 단서이지 현행 계약이 아니다.
2. lawgo 목록/상세 API 계약과 함께 type=HTML의 실제 화면·iframe·조문 링크·팝업·표 구조를 확인한다. 목록 API 성공만으로 HTML 보강 경로가 작동한다고 판단하지 않는다.
3. 기존 ID의 현재 대응 여부를 소수 대표 표본으로 대조한다. 본문만 있는 자료, 조문 다수, 이미지/첨부, 병합 번호, 판결/결정, 미연결·부분 실패를 포함한다. 검사 시각·응답/DOM hash·추출 결과·한계를 기록한다.
4. 제공된 정보를 보존하는 범위에서 현행 HTTP/세션/browser 방법을 선택한다. 접근 조건·호출 제한을 확인하고, 옛 selector를 맞춰 바꾸는 것만으로 취득 성공을 선언하지 않는다.
5. 예상 구조 부재·로그인/오류 페이지·필드 급감은 구조 변경 의심/취득 실패로 처리한다. 빈 판례·조문 없음·원문 삭제로 해석하지 않는다. 영향을 받은 adapter의 대량 작업을 멈추고 응답을 보존해 조사한다.
6. live 표본을 적절히 정리해 offline 회귀 fixture에 연결하고, ID/본문/조문/이미지 참조 검사를 통과한 뒤 작업량을 늘린다. 단순 HTTP 200이나 파일 생성은 내용 취득 성공 기준이 아니다.

현행 검증이 지연돼도 기존 archive의 읽기 전용 분석·보존 import 설계는 계속할 수 있다. 이 문서 갱신으로 실제 사이트 검증이나 수집 실행을 완료했다고 기록하지 않는다.
