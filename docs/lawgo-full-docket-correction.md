# lawgo 전체 사건번호 비교 교정 — 2026-09-15

## 근본 원인

1. scourt 상세에는 대표 번호 `csNoLstCtt`와 전체 번호 `mrgCsNoCtt`가 따로
   있다. 취득한 원본에는 둘 다 있었지만 worker는 대표 번호만 reader
   provenance의 `case_number`로 전달했다.
2. lawgo 검색 목록에는 대표 번호, 상세에는 병합·부수 사건을 포함한 전체
   번호가 올 수 있다. 기존 `exact_metadata`를 두 단계에 동일하게 적용해
   서로 다른 범위의 값을 비교했다.
3. 기존 숫자 축약용 docket parser는 `(본소)`, `(반소)`, `(울산)` 같은
   표기를 지원하지 않았다. 전체 번호를 단순히 전달하는 것만으로는 이
   경우를 해결할 수 없었다.
4. 기존 회귀에는 전체 병합 번호가 보존됐는데 downstream에서 대표 번호만
   사용하는 실제 35건의 조합이 없었다.

이는 source ID 변경이나 법률적 충돌을 뜻하지 않는다. 입력 전달과 비교
범위를 잘못 연결한 Python 로직의 문제다. 별도 감사에서 찾은 다른 ID 후보
300묶음과 번호 변경 3쌍까지 이 원인으로 설명하거나 자동 병합하지 않는다.

## 구현

- 새 규칙 `current-lawgo-4`. 신규 취득 worker가 `full_case_number`에
  전체 번호를 별도로 보존한다. 대표 번호·원문 값은 유지한다.
- 기존 reader 재처리도 `metadata_response_hash`로 보존 원본을 읽어 전체
  번호를 복구한다. 저장 계층의 hash 검증에 더해 source ID, 법원, 대표
  번호, 재판 종류, 날짜가 reader와 같은지 확인하고 다르면 명시적으로 실패한다.
- 목록은 대표 번호 또는 전체 번호로 후보를 좁힌다. 상세는 전체 번호가
  제공됐으면 전체 번호로만 비교한다. 부분 집합·첫 번호 일치로 확정하지 않는다.
- 일반 숫자 축약은 기존 전체 집합 비교를 유지한다. 병합 역할·지역 표기는
  제한된 문법의 전체 문자열이 그대로 같은 경우만 허용한다. 괄호 제거,
  법원 지원 제거, 임의 지역명 변경은 하지 않는다.
- 새 연결 plan에 규칙 버전, 원본 metadata artifact, 대표·전체 번호,
  상대 출처 번호와 상세 사건번호를 기록한다. 원문·이전 plan·reader는 불변이다.
- 정기 실행·무한 충돌 재시도는 추가하지 않았다. 이후 관리자 명령으로
  시작하는 신규 수집의 기존 영속 후속 체인에서 새 규칙이 자동 적용된다.
